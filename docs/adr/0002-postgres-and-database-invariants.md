# 0002. PostgreSQL, and the database enforces the rules that must never break

Status: accepted

## Context

Some mistakes are unacceptable in this domain: two classes booked into one room at the same time, more students than seats,
a student billed twice for one enrollment, a receipt number reused, a payment edited after the fact. Application code
checks these, but application code has bugs, and two requests can race each other. A rule that only the code enforces is a
rule that one missed case can break.

## Decision

Use PostgreSQL 18 with Drizzle ORM (SQL-first, typed, explicit about locking), and put every rule that must never be broken
into the database as well as the code:

- **Exclusion constraints** (`btree_gist`) stop academic years overlapping and stop a room or an instructor being booked
  for overlapping sessions.
- **Unique and partial-unique indexes** give "one live enrollment per student and class", "one invoice per enrollment",
  "one reminder per instalment and stage", "one issued certificate per enrollment", "one default payment plan".
- **CHECK constraints** hold arithmetic and state rules: an invoice's total equals its subtotal minus its discounts, an
  approval can't be decided by the person who requested it, a decided approval is final.
- **Triggers and grants** make recorded money append-only: the API's database role cannot delete or truncate money tables,
  and triggers refuse changes to an amount, number or line item (ADR 0007).
- **Row locks** (`FOR UPDATE`) serialize what must be serialized: the class row for seat counts, the invoice row for
  payments and discounts. Advisory locks cover things with no row to lock (a phone number being pre-registered, a batch
  import, a slug being chosen).
- **Three database roles.** `emis_migrator` owns the schema and runs migrations, `emis_app` (what the API and worker use)
  can read and write rows but not change the schema, `emis_readonly` can only select.
- **UUIDv7 primary keys** (time-ordered, generated by the database) and **keyset pagination** instead of OFFSET.

Every one of these has a test that would fail if the constraint were removed, and the concurrency ones were checked by
deliberately removing the lock and watching the test fail.

## Consequences

- Good: the rules hold no matter which code path, script or future feature touches the data. Races that are hard to
  reason about are settled by the database rather than by hope.
- Good: constraints document the domain. Reading the schema tells you what can never happen.
- Bad: more of the design lives in SQL migrations, which need hand-written parts (`emis_forbid_column_changes`, grants)
  that the ORM does not generate, and a violated constraint has to be translated into a friendly error.
- Bad: tied to PostgreSQL. That is deliberate; the alternatives below give up guarantees we rely on.

## Alternatives considered

- **Check only in application code.** Simpler, and wrong under concurrency.
- **An ORM that hides SQL** (Prisma, TypeORM). Less control over locking and constraints, which are the point here.
- **A document database.** No multi-row transactions with constraints of this kind.
